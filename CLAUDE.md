# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Firmware for a Raspberry Pi Pico (RP2040) based Christmas countdown clock. Custom PCB with 142 addressable RGB LEDs (arranged into seven-segment digits), an IR remote receiver/transmitter, an MPR121 capacitive touch controller (slider + 6 pads), a DCF77 time-signal receiver (driver implemented, see `lna` below) and (planned) power management peripherals. C++17 / C11, built with the Pico SDK and CMake, cross-compiled for ARM (no native/host build target exists).

## Build commands

This is an embedded, cross-compiled project — there is no host build, no test suite, and no linter configured in the repo.

Toolchain (Debian/Ubuntu):
```bash
sudo apt install cmake build-essential gcc-arm-none-eabi libnewlib-arm-none-eabi libstdc++-arm-none-eabi-newlib
```

Configure, either fetching the Pico SDK from git:
```bash
mkdir build && cd build
cmake -DPICO_SDK_FETCH_FROM_GIT=ON ..
```
or against a local SDK checkout at `~/pico-sdk` via the helper script (also sets up an ssh-agent from a `github-id` key file if present):
```bash
. start-env
```
or an explicit local SDK path:
```bash
mkdir build && cd build
cmake -DPICO_SDK_PATH=/path/to/pico-sdk ..
```

Build:
```bash
make -j$(nproc)
# or, matching CI: cmake --build build
```

Output is `build/app/ChristmasClock.uf2` (and related outputs from `pico_add_extra_outputs`). Deploy by holding BOOTSEL while plugging in the Pico, then copying the `.uf2` file onto the mass-storage device that appears.

CI (`.github/workflows/build.yml`) runs the same `cmake -B build . && cmake --build build` inside the Docker action at `.github/actions/pico-build` (Alpine + `gcc-arm-none-eabi`, Pico SDK cloned fresh into the image) and uploads the resulting `.uf2` as an artifact. It only triggers on `master` pushes/PRs.

## Architecture

**CMake layout**: root `CMakeLists.txt` calls `pico_sdk_init()` then adds `drivers/` and `app/`. `drivers/CMakeLists.txt` adds five INTERFACE libraries — `ir`, `led`, `lna`, `power`, `touch` — each defined by its own `<name>.cmake`. `app/CMakeLists.txt` globs all `app/include/**/*.h*` and `app/src/**/*.c*` into the `ChristmasClock` executable and links all five driver libraries. Adding a new source file under `app/` or a driver's `src/`/`include/` is picked up automatically by the glob; no CMakeLists edits needed there.

**Entry point / main loop** (`app/src/Main.cpp`): a single `while(true)` loop that (1) ticks the countdown once per second, (2) transmits the current time via IR every second, (2b) polls the DCF77 receiver (`LNA::PollSync()`, every loop iteration) and prints a newly confirmed wall-clock time plus frame stats to stdout — **not** wired into the display or `ChristmasClock` state yet, since the display only shows an MM:SS countdown and what the DCF77 time should do there (HH:MM mode? countdown to Dec 24?) is undecided, (3) polls for IR events and updates the LED display roughly every 20 loop iterations (~200ms), with a 10ms sleep per iteration.

**App state machine** (`app/include/ChristmasClock.hpp` / `app/src/ChristmasClock.cpp`): `ChristmasClock::ChristmasClock` owns the `LED`/`SevenSeg` display, the `Touch` controller, and all UI state (on/off, running/paused, brightness index, menu mode, countdown/warning/finishing thresholds). It boots **paused** (`_running(false)`) with a 5-minute countdown (`_countdown`/`_time` = 300s, `_countdown_warning`/`_countdown_finishing` = 100/50s, i.e. the same countdown/3, warning/2 proportions `SetCountdown()` uses) — nothing ticks until something explicitly starts it (TP4, see below). `EvaluateEvent(NECEvent)` is the central dispatcher for remote-control input: ON_OFF, VOL_UP/DOWN, ENTER_MENU (toggles a numeric-entry mode where NUM_0-9 build up a BCD-encoded MM:SS value via `ConvertTimeToNumber`/`NumberToConvertTime`), and any other event resets (but does not start/stop) the countdown. Display color escalates green → orange → red as the countdown approaches `_countdown_warning`/`_countdown_finishing`. `Tick()` (called once/sec from `Main.cpp`) only decrements `_time` while `_running` is true; `_time` is allowed to go negative (`SevenSeg` has a dedicated negative-sign glyph) — there's no floor.

Brightness (`_vol_index`, indexes into `_brightness[20]`) is clamped everywhere to `[0, MAX_VOL_INDEX]`, not the full table — the upper end of `_brightness` (up to 255) was blindingly bright with 142 LEDs, so `MAX_VOL_INDEX` (currently 8, i.e. max gain 22) caps VOL_UP, the touch-slider mapping, and the boot-time default alike. Bump this constant (and/or the initial `_vol_index`) if the usable range needs to change.

`Update()` (called ~5Hz) also polls the `Touch` driver every cycle, independent of `_is_in_menu`/`_is_on`: a held slider touch continuously overwrites `_vol_index`/brightness (same state VOL_UP/DOWN uses, so IR remote and slider can't fight — whichever moved last wins), and newly-pressed pad edges (`Touch::GetPressedPads()`) are dispatched once per tap: TP1/TP2 = -1/+1 minute, TP3 = Reset, TP4 = toggle `_running` (start/pause — the only way the countdown starts), TP5/TP6 = +1/-1 second.

**Idle screensaver (2026-09-15)**: `_idle_seconds` counts seconds (incremented once/sec in `Tick()`) since the last activity, where "activity" is defined as: the countdown running (`_running`), a touch pad press or slider touch (`Update()`), or any non-`NO_EVENT` IR remote event (`EvaluateEvent()`) — each of these resets it to 0. After `MATRIX_IDLE_TIMEOUT_S` (10s) with none of those, `_matrix_active` latches true and `Update()` renders `MatrixEffect` instead of the countdown/menu display (checked before the `_is_in_menu` branch, so it can also cover a menu left open and unattended); any of the same three activity sources immediately clears `_matrix_active` again and returns to the previous display next frame. Including IR events in "activity" was an intentional addition beyond the original ask (just countdown-running + touch) — without it, pressing a remote button while the screensaver is up wouldn't visibly do anything until the *next* button press.

**Snake effect toggle (2026-09-15)**: holding TP1+TP6 together (both bits set in the same `GetPressedPads()` poll) toggles `_snake_active`, which shows `SnakeEffect` instead of everything else — checked in `Update()` *before* `_matrix_active`, so it takes priority over the idle screensaver and stays up until the same gesture toggles it off again (it doesn't auto-cancel on other activity the way `_matrix_active` does). Since TP1/TP6 individually already mean "-1 minute"/"-1 second", the combo is special-cased *instead of* those two actions (not in addition to them) to avoid also nudging the countdown by -61s every time someone triggers the easter egg.

**IR driver** (`drivers/ir/`): NEC-protocol receive/transmit implemented via PIO state machines (`pio/*.pio`, compiled to headers under `include/generated/` by `pico_generate_pio_header` — these generated headers are checked into the repo, so PIO source and generated header must be kept in sync manually). `ErrorCorrection` adds a Manchester-style layer on top of the raw NEC payload. `NECEventMapper` (`INECReceiver` → `NECEvent`) maintains lookup tables for three different physical remotes (Terratec, DVB-T, Samsung codes) and normalizes them to a single `NECEvent` enum consumed by the app layer.

**LED driver** (`drivers/led/`): drives 142 WS2812B-2020 addressable LEDs over PIO/DMA (`LED` class, `pio/led.pio`). The LEDs are *not* a dense dot-matrix despite the 33x13 addressing grid — they're only physically populated where a seven-segment digit's segments are (4 digit blocks at bitmap x-offsets 0/8/18/26, each digit built from 5-pixel-long segment strokes, plus a 2-pixel colon at x=16) — the `lines`/`snake` tables in `LED`/`LEDvertical` encode exactly that sparse layout and its boustrophedon wiring order. `SevenSeg` draws digits/points onto that matrix on top of the `LED`/`Bitmap` primitives, using static per-segment coordinate tables and a BCD decode table (`_bcdDecode` already covers all 16 hex values 0-9/A-F, though only `SetDigit`/`SetNumber` expose decimal today). `ColorGRBa` is the pixel color type; `bitmap.hpp`/`base64.hpp` support loading/encoding bitmap patterns.

**Display orientation** (confirmed 2026-09-15, board held with the middle mounting screw on its long edge at the bottom — see `hole_positions` in `hardware/enclosure/ChristmasClock_Enclosure.scad`, the `(99.952, 7.163)` entry is exactly that screw): cross-checked the LED footprint canvas positions in `hardware/6-PCB_PCB_ChristmasClock_final_layout.json` (`DIGIT_0_DI`...`DIGIT_3_DO` pads increase in canvas X in that same order; the digit-0 top-segment LED sits at a smaller canvas Y than its own upper-vertical-segment LEDs further down) against the same board-local frame the mounting holes use. Result: **no flip needed** — increasing bitmap x already runs left-to-right and increasing bitmap y already runs top-to-bottom in that held orientation, exactly like the existing `SetDigit1..4`/MM:SS layout (which already had to be right-reading for the shipped countdown display to make sense — a second, independent confirmation of the same result). Any future pixel-addressed feature (marquee, animations) can use `LED`/`Bitmap` x/y directly with this orientation.

**Marquee/ticker** (`SevenSeg::SetMarqueeWindow(text, offset)`): given the sparse seven-segment-only LED layout above, a real per-pixel scrolling font isn't physically renderable (there are no LEDs in the gaps between digit blocks) — the practical alternative implemented is a 4-character *window* into a longer string, advanced one whole character per call by incrementing `offset` (e.g. once per timer tick from wherever the caller decides to drive it — not wired into `Main.cpp`/`ChristmasClock`'s event loop yet, that's a separate decision). Character set is necessarily limited to what a seven-segment digit can render: `0-9` and hex `a-f`/`A-F` (via `CharToHexValue`); anything else (e.g. a space used as a loop separator between repeats of the message) is shown blank via `ClearDigit`. That also means "words" are effectively limited to hex-speak (`BEEF`, `CAFE`, `DEAD`, `FACE`, `FADE`, ...).

**Touch driver** (`drivers/touch/`): real MPR121 capacitive-touch driver over I2C1 (GPIO18 SDA / GPIO19 SCL, address 0x5A — see hardware section for how that was derived). `Touch::GetSliderPosition()` returns `std::optional<float>` (0.0-1.0, `nullopt` if untouched), computed as a weighted centroid over baseline-minus-filtered delta across the slider's 6 electrodes (ELE3-ELE8). `Touch::GetPressedPads()` returns a bitmask of `TouchPad` enum values (TP1-TP6, mapped to ELE0-2/ELE9-11) for pads that transitioned untouched→touched since the last call, i.e. one hit per tap (no auto-repeat while held). Register init follows the standard MPR121/AN3944 default config (thresholds, filter, AFE) — see `Touch::Init()` if electrodes need retuning for sensitivity.

**Persistent configuration**: not implemented — there is no filesystem or flash-write code anywhere in the firmware today; all settings (`MAX_VOL_INDEX`, default countdown, etc.) are compile-time constants or RAM-only state that resets on power loss. No SD card or other removable storage exists on this board. If this is needed, the external QSPI boot flash (`U1`, W25Q64JVXGIQ, 8MB — the firmware `.uf2` only uses ~700KB of it) has plenty of spare room for it. Two options, not yet decided between:
1. **Raw `hardware_flash` struct**: reserve a fixed offset near the end of flash, read/write a small config struct directly with `flash_range_erase`/`flash_range_program`. Simple, no dependency, but you own sector-erase-before-write (4KB sectors), wear leveling (NOR flash has a limited erase-cycle count), and disabling interrupts/avoiding XIP conflicts during the write.
2. **A small flash filesystem** (e.g. LittleFS): gives actual "files", more ergonomic, but real integration effort — likely overkill for a handful of settings.
For the amount of config this app has (a few numbers), option 1 is the recommended starting point.
**Decided not to persist the DCF77 time (2026-09-29)**: the idea was to store the last synced time in flash so the next boot syncs faster. There is no battery-backed RTC, so a stored time is stale by an unknown power-off duration and can't be shown directly — it could only serve as a plausibility check that lets the decoder accept a *single* valid frame instead of waiting for the 2-frame confirmation, saving about 1 minute (first sync ~1-2 min instead of ~3), and less than that isn't possible without a decoded frame. The user judged that not worth it and left it as is. If revisited: write at most ~hourly, and use `flash_safe_execute` (the 10ms sampling timer callback runs from flash and would crash during an erase). A real fix would be a battery + RTC chip (PCB change).

**power driver**: currently a stub. It exposes a single `SampleDriverFunction()` that only prints to stdout (`drivers/power/src/power.cpp`) — the real hardware exists on the PCB (see below) but the driver logic has not been implemented yet. Don't assume it does anything functional.

**`lna` driver / DCF77 sync (implemented 2026-09-29, host-tested only — not yet run against the real receiver)**: `lna`'s hardware is a DCF77 (77.5kHz longwave time signal) receiver front-end, not an audio amplifier — see hardware section. The analog front-end on the LNA sheet already does the full AM demodulation in hardware — a two-stage comparator (U9, GS8052-SR) squares the amplified carrier against a mid-supply reference (`VGND`, from the R33/R34 divider), then low-pass-filters that square wave (R37+C184, R38+C185) and re-thresholds it in the second comparator to produce a clean digital pulse train on the `DCF77` net, which crosses to the RP2040 sheet as a single GPIO input (near the D17-D19 group) — no further analog work needed, only firmware.
- **Pin**: the `DCF77` net goes through a 47Ω series resistor to the net `A0`, which is **GPIO26** (`GPIO26_ADC0` pin, used as a plain digital input; found by tracing the `A0` net port to the RP2040 symbol pin in `1-Schematic_ChristmasClock.json`). `LNA::kDefaultPin`.
- **Split** (`drivers/lna/`): `DCF77Decoder` (`include/DCF77Decoder.hpp`, `src/DCF77Decoder.cpp`) is a pure, hardware-independent state machine — `Feed(level, now_ms)` at a fixed rate — so it can be compiled and tested natively on the PC (`g++ -std=c++17 -Idrivers/lna/include test.cpp drivers/lna/src/DCF77Decoder.cpp`; the throwaway test used for verification is not in the repo). `LNA` (`lna.hpp/.cpp`) is the thin Pico part: `gpio_init` (input, pulls off) plus a 10ms `add_repeating_timer_ms(-10, ...)` whose IRQ-context callback calls `Feed()`. `lna.cmake` lists both `.cpp` files explicitly (driver sources are *not* globbed, unlike `app/`).
- **Decoder**: sampling (timer) was chosen over GPIO edge interrupts for noise robustness. A level change counts only after 2 consecutive equal samples (20ms; edge time = first differing sample, so both edges shift equally and widths stay accurate). Phase widths 50-150ms = bit 0, 150-260ms = bit 1; anything else (800-900ms phases, noise) is ignored. **Polarity is auto-detected** (vote on which level shows 100/200ms phases), so active-high vs active-low comparator output doesn't matter. The minute mark is a ~2s gap between pulse starts (1750-2250ms); normal seconds are 900-1100ms apart; anything else drops sync until the next minute mark. The frame decoded at a minute mark describes the minute starting at *that* mark (DCF77 sends the upcoming minute). Checks: bit0=0, bit20=1, Z1≠Z2, 3 even parities, BCD ranges, day ≤ days-in-month. A time is published only when it equals the previous frame + 1 minute (`AddMinute`, full calendar rollover incl. leap years) — so the first sync takes ~3 minutes under good reception; a bad or lost frame restarts the chain. Across a DST change the hour jumps, so that confirmation fails once and the chain restarts.
- **API**: `LNA::PollSync()` returns `std::optional<Synced{time, age_ms}>` once per confirmed minute — `time` is the wall-clock time (year/month/day/weekday/hour/minute/cest) at second 0 of that minute, `age_ms` is how long ago that mark was (add to seconds). `LNA::GetStats()` returns `frames_ok/bad/lost` counters for judging reception quality. Both take an IRQ-safe copy (`save_and_disable_interrupts`).
- **Verified**: firmware builds (`build/app/ChristmasClock.uf2`), decoder passes a native simulated-signal test (year rollover 2026→2027, 32-bit ms wrap, both polarities, sparse single-sample glitches, corrupted parity frame rejected without bogus sync, pure noise never syncs). **Not yet tested on real hardware** — with the substitute 3.3mH/1.2nF coil tank below, check `frames_ok/bad/lost` on the serial console, ideally near a window.

**LNA alternate BOM (in use, 2026-09-15)**: the original receiving-coil inductor (Mouser 871-B82500CA2 / TDK B82500C0000A002, 3.9mH, axial) is obsolete and wasn't sourceable as an exact replacement, so the board is being built with substitutes for the coil's whole LC tank: a **3.3mH axial inductor** in place of the coil, and **C170/C171/C172/C173 changed from 1nF to 1.2nF each** (4×1.2nF = 4.8nF total, up from 4×1nF = 4nF). Derivation: the tank's resonant frequency depends on L·C, so a smaller L needs proportionally more C to land on the same frequency — C_new(total) = C_old(total) × L_old/L_new = 4nF × 3.9/3.3 ≈ 4.73nF; 4×1.2nF = 4.8nF is within ~1.5% of that target (replacing only one of the four caps, e.g. 3×1nF+1×1.2nF=4.2nF, would undershoot by ~11% capacitance / ~6% frequency — worth avoiding since 100pcs of the 1.2nF part were ordered specifically to redo all four). This is a workable substitution, not a precision one: the front end is a broadband envelope detector (not a sharp filter) and the original coil/cap tolerances were already ±10-20%, so exact resonance isn't critical.

**Hardware** (`hardware/`): EasyEDA schematic + PCB export. The JSON files were reformatted with `json.dump(indent=2)` (one shape per line) so they're `Read`/`grep`-able directly instead of one 5MB+ minified line per file — EasyEDA re-parses pretty-printed JSON fine, so redo this if a future export re-minifies them (open via EasyEDA, see `hardware/README.txt`, for actual editing). The schematic has 7 sheets that map 1:1 to the driver/app split above: `Digits` (142x WS2812B-2020 + decoupling), `RP2040` (MCU, SPI flash, USB-C, boot/reset), `GPIO` (breakout + SWD debug header + `DIGITS_IN`/`DIGITS_OUT` daisy-chain header), `Touch` (MPR121 + pads/slider), `Power` (buck converter + two 3.3V LDOs + load switch), `LNA` (DCF77 longwave receiver front-end, *not* an audio amp — see net label `DCF77` and the "UKW Drossel als Empfangsspule" annotation), `IRDa` (IR receive/transmit front-end). `6-PCB_PCB_ChristmasClock_final_layout.json` is the current PCB layout (2-layer, ~200mm x 100mm); files `2` through `5` are earlier layout backups kept for history.

Cross-sheet nets are carried by `F~part_netLabel_netPort~...` shapes (a name like `TOUCH_SDA` recurs at every wire endpoint it's electrically joined to, across sheets — there's no hierarchical sheet-symbol port). Plain `N~...` shapes are same-sheet-only net labels; `O~...` shapes near pins are no-connect flags, not ports. On the RP2040 sheet, generic pin names (`D18`, `A0`, etc.) map 1:1 to GPIO numbers — cross-check against the RP2040 GPIO function table when a mapping matters (that's how GPIO18/19 for I2C1 SDA/SCL were confirmed for the Touch driver above).

**Where mechanical/physical PCB data actually lives:** the EasyEDA PCB JSON (`hardware/6-PCB_PCB_ChristmasClock_final_layout.json`) has **no mounting-hole or drill geometry at all** — exhaustively checked, no top-level `HOLE`/`VIA`/`PAD` shape and no nested footprint pad anywhere has a hole large enough to be a mounting screw. That data only exists in a **Gerber/Excellon export** (a zip containing `.GKO`/`.GBL`/`.DRL` etc., e.g. `hardware/Gerber_ChristmasClock_PCB_ChristmasClock_2026-09-10.zip`): board outline is `Gerber_BoardOutlineLayer.GKO`, non-plated mounting holes are in `Drill_NPTH_Through.DRL` (diameter from the tool table, centers from the `X..Y..` lines). Two gotchas when parsing Gerber/Excellon files: (1) different files in the same export can use different coordinate formats (check each file's own `;FILE_FORMAT=` comment, e.g. drill files here are `2:4` while the outline is `3:6` — both in inches) and (2) Gerber Y increases *downward* from the file's own origin, which does not necessarily match how the physical board is held/viewed — mirror Y (`y_true = board_h - y_gerber`) if positions look flipped against the real board (confirmed needed for this board; X was already correct unmirrored).

**Enclosure**: `hardware/enclosure/ChristmasClock_Enclosure.scad` is a parametric OpenSCAD model built from the Gerber-derived board outline (200×100mm) and mounting-hole positions above. It currently defines two independently-printable parts, selected via the `part` variable at the top of the file (`"base"`, `"battbox_base"`, or `"both"` for both laid out side by side):
- `battbox_base()` — the battery box: sits flat on the table, holds a side-by-side 4×AA holder in a retaining nest. No separate lid.
- `base_with_stand()` — the PCB tray, which *is* the battery box's lid (v4, 2026-09-11 — see below). Screws go in from the front, through the PCB, and thread into M3 hex nuts captured in pockets recessed into the underside of the (thickened, 4mm) floor — no nut boss protrudes below the floor, so the print bed contact stays flat.
- **v4 hinge redesign (2026-09-11)**: originally the battery box was a separate part with its own press-fit ("Steck-") cap, hinged to the base as a kickstand leg for tilting the display. User asked to drop the battery box's separate lid entirely and have the PCB tray double as its lid instead — closed, the tray sits flush on top of the box with the PCB facing *down* (PCB and batteries both fully enclosed, e.g. for storage/transport); opened, it swings up past vertical to a reclined display angle with the PCB facing up/out again — same part sizes/footprint as before, only the hinge attachment moved. Still the same M3 bolt+nut friction hinge (`hinge_r=3.5`/`hinge_margin=8`, tuned in the v2/v3 rounds below), just re-anchored: the pivot sits `hinge_margin` out from the battery box's own y=0 wall, at the box's *rim* height (`battbox_base_h`) instead of bed level. The box gets a 2-ear fork there (`box_ears()`, same L-bracket-plus-knuckle shape as before); the tray gets a single tab reaching from beyond its own *far* edge (`lid_tab()`, at `y = outer_h + hinge_margin`) so its body starts out clear of the box rather than overlapping it. Neither knuckle touches the print bed any more (both sit near their own part's rim, carried by a wall-bonded plate), so the old bed-adhesion foot trick isn't needed here.
  - Verified with `hardware/enclosure/scratch/lid_sweep_final.py` (places the real `base_with_stand()` + `battbox_base()` — hinge features included — at the real assembled pose for a swept angle, `intersection()`s them, counts STL facets — 0 = clean). In that script's own theta convention, **theta=180° is CLOSED** (flush on top of the box, PCB down, 0 facets) and it stays clean all the way through at least theta=350° — opening swings up through vertical (~270°) to a reclined angle; theta=315° (180+135) matches "tilt back up to 135° from closed" with real margin to spare. (theta=0 in that same script would nest the tray *inside* the box's cavity, colliding with the battery nest — not a usable reference angle, ignore it.)
  - Every hinge-facing part (`box_ears()` on the battery box, `lid_tab()` on the tray) is built as an **L-bracket**, not a free-floating round knuckle: a vertical stroke bonded flush to the part's own wall across its *full height*, plus (in the original bed-level version) a short horizontal foot reaching only as far as the knuckle's z=0 tangent point — that foot isn't needed any more since v4's knuckles sit at each part's rim, not the bed. Keep the L-bracket wall-bond pattern if the hinge geometry changes again; a plain knuckle floating off the wall prints as an unsupported island.
  - **Knuckle size** (`hinge_r`/`hinge_margin`) history, unaffected by the v4 relocation — only the anchor point (bed vs. rim) changed, not these two numbers: the first version used a 26mm-diameter knuckle (`hinge_margin=12`/`ear_r=13`) centered 13mm off the wall — printed and barely moved, since a disc that big sweeps into the mating shell's wall at almost any angle. v2 shrank it to `hinge_r=4.5`/`hinge_margin=8` (sized just for the M3 hole, pulled in close to the wall, door-hinge-style). v3 (after comparing against a MakerWorld reference hinge box the user found, whose knuckle sits nearly flush with the wall) grid-searched `hinge_r`/`hinge_margin` pairs: shrinking `hinge_margin` below 8 made the range *worse*, but shrinking `hinge_r` alone at the same `hinge_margin=8` kept extending it — `hinge_r=3.5` (current default, ~1.8mm wall left around the M3 hole) was the best range/strength tradeoff (`hinge_r=3.0` reaches further but drops to ~1.3mm wall, too thin for repeated hinge torque).
  - This is **not** a flush-closing-*and*-wide-open-range hinge from a single *bed-level* pivot — the battery box (23mm thick) is ~2.4x the base's own thickness (9.6mm), and centering a bed-level pivot between the two thicknesses fixes a flush 180° close but breaks the open range instead (both parts' near-hinge bulk then sweeps the same radius from the pivot; tested and rejected in v2/v3, see [[project_enclosure_hinge_v2]]). v4 sidesteps that specific conflict by anchoring at the box's *rim* instead of bed level, since that's a fundamentally different geometry (thin lid swinging clear of a tall fixed box, not two mismatched thicknesses sharing one low pivot) — don't reuse the v2/v3 "can't have both" conclusion here, it was about the old bed-level arrangement specifically.
- Component heights/clearances (`bottom_clearance`, battery box `batt_clear`, etc.) are estimates, not measured from the Gerber data — adjust to match the real stack-up.
- **Connector cutouts** in the tray's back wall (`connector_cutouts` array, at case `y=outer_h`): USB-C and the external power pins (`EXT_VIN`/`GND`, a 2-pin castellated edge pair meant for a pluggable screw terminal) both sit right at the board's front edge and need the case wall open there, or they have to be cut free with a knife after printing (confirmed on a real print). Positions/widths are derived from the real copper pad extents in `hardware/6-PCB_PCB_ChristmasClock_final_layout.json` (board-local = `(canvas - [4020.5, 3055.5]) * 0.254mm`, confirmed against the Gerber board outline), sized to each connector's outermost solder points + 1mm. Only the top half of the wall height is opened (rim down to the PCB surface); the floor-level half stays solid. Since v4, `lid_tab()` is on this same wall (both at `y=outer_h`) — confirmed no conflict, the tab sits centered in X (~98–102mm) while both cutouts are well to the right (159–183mm).

OpenSCAD (2021.01) is installed in this environment (`/usr/bin/openscad`) — render directly rather than only hand-tracing geometry (`openscad -o out.stl -D 'part="base"' file.scad`, then grep stderr for `Simple:`/`Volumes:`/`WARNING`). `Simple: yes` only confirms locally-manifold geometry, not that a union actually fused: two solids touching at an exact tangent (zero-volume) face render fine but show up as an extra disconnected `Volumes:` count (a single properly-fused part reports `Volumes: 2` — background + one solid). Whenever two pieces are meant to bond, give them a deliberate ~0.5–1.5mm overlap rather than exactly-coincident coordinates. To sanity-check two separate parts for a real assembly collision, `intersection()` them (with one flipped/translated into its actual assembled pose, not its print pose) and check the result isn't just a many-vertex solid — a couple of stray vertices is a harmless degenerate touch, not a collision.
